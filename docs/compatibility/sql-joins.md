# SQL joins

Table reference, join syntax, join semantics, lateral derived table, and join metadata compatibility.

| Feature | Status | Notes |
| --- | --- | --- |
| Table references | 🟡 | Limited descriptor-backed base-table references in plain `SELECT` with optional `AS alias` or bare aliases, limited validated/no-op index hints, multi-source inner/cartesian/`STRAIGHT_JOIN` chains, pure multi-source comma lists, limited multi-source left outer join chains, and two-source right outer joins; no mixed comma/explicit join precedence, derived tables, table functions, parenthesized table references, or partitions |
| Inner joins | 🟡 | Limited `JOIN`, `INNER JOIN`, `CROSS JOIN`, `STRAIGHT_JOIN`, and comma joins in descriptor-backed plain `SELECT`, including three-or-more-source inner/cartesian/straight chains and pure comma lists, with optional one-column same-family integer or ASCII string descriptor equality `ON` plus an optional `AND`-conjoined descriptor predicate from the existing joined predicate subset, no `ON` for cartesian products, or limited same-family descriptor-column equality in `WHERE` for comma/inner join filtering; supports projection, qualified wildcards, `WHERE`, descriptor-column `ORDER BY`, `LIMIT`, and limited `SQL_CALC_FOUND_ROWS` over joined sources, plus existing grouped aggregates over joined source envelopes. `USING (column[, ...])` is parser-admitted for `JOIN`, `INNER JOIN`, `CROSS JOIN`, and `STRAIGHT_JOIN` and returns an explicit unsupported diagnostic before planning. No executable `USING`, mixed comma/explicit precedence, mixed-type `ON`/column-to-column comparisons, arbitrary `ON` predicates, arbitrary column-to-column `WHERE`, multi-source right/full outer joins, distinct joins, full grouping, optimizer join-order forcing, or expression projection |
| Left outer joins | 🟡 | Limited `LEFT JOIN` and `LEFT OUTER JOIN` chains in descriptor-backed `SELECT`, with required one-column same-family integer or ASCII string descriptor equality `ON` plus an optional `AND`-conjoined descriptor predicate from the existing joined predicate subset; preserves left rows, null-extends unmatched right descriptor columns, and supports projection, `WHERE`, descriptor-column `ORDER BY`, `LIMIT`, limited `SQL_CALC_FOUND_ROWS`, and grouped primary-key-dependent projections over joined sources. `USING (column[, ...])` is parser-admitted and returns an explicit unsupported diagnostic. No executable `USING`, natural-join semantics, full outer joins, mixed-type `ON` comparisons, arbitrary `ON` predicates, distinct joins, full grouping, or expression projection |
| Right outer joins | 🟡 | Limited two-source `RIGHT JOIN` and `RIGHT OUTER JOIN` in plain descriptor-backed `SELECT`, with required one-column same-family integer or ASCII string descriptor equality `ON` plus an optional `AND`-conjoined descriptor predicate from the existing joined predicate subset; preserves right rows, null-extends unmatched left descriptor columns, keeps `SELECT *` syntactic left-then-right column order, and supports projection, `WHERE`, descriptor-column `ORDER BY`, and `LIMIT` over joined sources. `USING (column[, ...])` is parser-admitted and returns an explicit unsupported diagnostic. No executable `USING`, natural-join semantics, joined DML right joins, grouped right joins, full outer joins, mixed-type `ON` comparisons, arbitrary `ON` predicates, multi-source right outer chains, distinct joins, full grouping, or expression projection |
| Full outer joins | ❌ | MySQL-style diagnostics for unsupported `FULL OUTER JOIN` syntax; no full outer null-extension emulation. Plain `FULL JOIN` is not treated as a full-outer operator in the current subset because MySQL can parse `FULL` as a source alias followed by an ordinary `JOIN` |
| Natural joins | ⚪ | Parser-admitted `NATURAL JOIN`, `NATURAL INNER JOIN`, `NATURAL LEFT [OUTER] JOIN`, and `NATURAL RIGHT [OUTER] JOIN` return explicit unsupported diagnostics before planning; no inferred `USING` column lists, coalesced wildcard output, null-extension semantics, DML join semantics, or metadata. See [parser corpus query-expression surfaces](../specs/parser-corpus-query-expression-surfaces/specs.md) |
| `STRAIGHT_JOIN` | 🟡 | Accepted as an inner-join operator in the current descriptor-backed plain `SELECT`, joined `DELETE`, and joined `UPDATE` envelopes; MyLite does not implement join-order optimizer forcing or physical plan-shape guarantees |
| Lateral derived tables | ❌ | LATERAL derived table correlation rules |
