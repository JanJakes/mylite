# End-to-End Performance Review, July 2026

## Scope and method

This review closes the WordPress runtime performance plan based on the audit at
`11b6a43d28619133edbf9bbb289263cc66b249b5`. The comparison baseline is that
commit with benchmark-only commits `5c820af43`, `912b1d59e`, and `988f7f83c`
applied so both binaries run the same scenarios and latency instrumentation.
The measured implementation head is `4a6487677448f73c5c20b544e55e1ba604afd3ee`.
The final review then added two correctness-only fixes without changing the
measured optimization design.

Both binaries were GCC 14.2 Release builds. Runs were pinned to CPU 8 on an
18-vCPU AMD EPYC KVM guest running Linux 6.12. The request comparisons used
seven samples of 500 complete requests. CPU-focused runs used tmpfs; durable
runs used the ext4 filesystem containing the project. Results below are sample
medians unless stated otherwise.

## Completed implementation work

The five original implementation items are complete:

1. Read-only transactions use deferred SQLite transactions instead of reserving
   the writer lock (`f1c0cd11f`). A bounded busy wait and a live read-cursor/write
   concurrency regression cover transient lock contention (`b6aa44c4f`).
2. Large `IN` lists and analogous expression walkers traverse linked AST children
   linearly (`bc16ec1f8`, `654d82ddc`).
3. SELECT plan arrays grow geometrically and plans borrow generation-pinned
   source metadata instead of cloning large descriptors (`2eaf6edba`).
4. Table-backed SELECTs synchronize the catalog once, after opening the read
   snapshot (`be32925f5`).
5. Cold open validates the catalog shape without parsing SQL, and mysqli
   prepared SELECTs buffer directly from cursors (`a2e71b224`, `bc5d58a73`).

Profiling then identified repeated SQLite parsing outside the original five.
Statement transactions now cache their fixed control programs (`99b6820dc`),
and row-scalar, aggregate, rollup, and `SQL_CALC_FOUND_ROWS` paths reuse generated
SQLite statements (`4a6487677`). A 55,000-query gprof run reduced
`sqlite3RunParser` calls from 110,619 to 585, a 99.5% reduction.

The implementation also fixed a source-span lifetime defect exposed by ASan in
parser retry coverage (`3523faa0a`).

The final review found and fixed two additional allocator-lifecycle defects:

- Predicate merging could shrink an allocation without updating its recorded
  capacity, allowing the following logical node to overrun the buffer
  (`5083f677a`).
- The bounded AST chunk cache was thread-local and retained a chunk after a
  worker exited. It is now process-bounded and thread-safe, preventing cache
  memory from multiplying with worker count (`0275b55a7`).

## Completed closure gates

The four measurement and validation gates are complete:

1. Targeted cold-open, large-`IN`, wide-projection, cache-saturation, and
   concurrent reader/writer scenarios are available (`5c820af43`).
2. The medium WordPress fixture covers nine tables and eleven representative
   frontend queries (`988f7f83c`).
3. Request p50, p95, p99, and maximum latency are reported per sample
   (`912b1d59e`), and both tmpfs and ext4 runs were collected.
4. The audited baseline and current Release builds were run with the same
   harness, CPU affinity, iteration counts, and sample counts.

## Results

| Scenario | Audited baseline | Current | Change |
| --- | ---: | ---: | ---: |
| Cold open | 1,049.485 us/open | 897.182 us/open | 14.5% faster |
| 4,096-value `IN` | 167,728.645 us/query | 4,826.755 us/query | 34.7x faster |
| 128-column projection | 3,520.548 us/query | 342.329 us/query | 10.3x faster |
| Catalog cache saturation | 66.444 us/query | 45.879 us/query | 30.9% faster |
| Six-query frontend | 108.603 us/query | 84.816 us/query | 21.9% faster |
| Eleven-query medium frontend | 142.532 us/query | 91.542 us/query | 35.8% faster |

For the ext4 medium fixture, the median-of-samples request p50/p95/p99 changed
from 1.229/2.427/7.547 ms to 0.850/1.473/5.104 ms. Tail measurements remain
host-sensitive, but all three percentiles and the per-query median improved.

The final concurrent gate completed 14,000 operations across seven samples with
zero errors and a median 118.122 us/operation. The audited baseline produced
transient internal lock errors under the same reader/writer overlap.

The ext4 write fixture is dominated by four durable autocommit cycles per
request. Its baseline samples ranged from 3.302 to 7.503 ms/query and current
samples from 3.473 to 6.052 ms/query, so these runs do not establish a meaningful
CPU-side before/after difference. Per-query tmpfs isolation showed improvements
on the read, both updates, and delete; the upsert remained within run-to-run
variance. Changing synchronization or transaction semantics solely to improve
that number would weaken durability or MySQL autocommit compatibility.

## Post-review metadata-scale follow-up

Commit `27962f62d` completed the metadata iterator work identified by the later
whole-project assessment. Metadata predicates now run against provider rows
before allocation. Unordered, ungrouped projections append directly to the
final result; `COUNT(*)` retains only a counter; ordered and grouped queries
retain only required columns; and LIMIT terminates provider enumeration when
result ordering permits it. Queries whose LIMIT guarantees an empty result do
not enter providers.

A controlled comparison used GCC 14.2 Release builds at baseline `451a812b4`
and `27962f62d`, pinned to CPU 3, with seven samples of 5,000 iterations and two
warmups. The five-query `runtime.wp_metadata_hot` median changed from 74.164 to
72.655 us/query, a 2.0% improvement. Its directly affected
`INFORMATION_SCHEMA.COLUMNS` query changed from 72.242 to 62.351 us/query, a
13.7% improvement. The change passed all 134 INFORMATION_SCHEMA, Performance
Schema, and sys tests plus the focused ASan/LeakSanitizer test.

## Residual assessment

No remaining finding is a significant successful WordPress frontend runtime
bottleneck in the measured fixtures. The successful-query lexer/parser is a
small fraction of request time, descriptor and linked-list scaling defects are
removed, SQLite programs are reused, catalog synchronization is no longer
duplicated, and concurrent reads and writes no longer fail immediately.

The following narrower areas remain candidates only when their workloads become
priorities:

- Native reusable MyLite plans for repeated `mysqli_stmt` execution. WordPress
  uses literal SQL through `wpdb::prepare()`, so this is not on the measured path.
- High-cardinality metadata queries with ordering or grouping still retain the
  required sort/group keys. Further work there should start from a measured
  administration workload because unordered queries now stream and exact
  COLUMNS/STATISTICS lookups are direct.
- Shared parser retry tokenization for large invalid SQL and reuse of Lemon
  parser storage. These do not affect successful WordPress-shaped queries enough
  to justify added lifetime complexity now.
- High-cardinality PROCESSLIST snapshot synchronization and sorting. This is an
  administrative concurrency concern, not a frontend request hot path.
- Storage-engine durability research for autocommit-heavy writes. Treat this as
  a separate format/durability project, not a CPU micro-optimization.

The WordPress runtime CPU-performance chapter can close. Future optimization
work should start from a workload that demonstrates one of the residual areas
in end-to-end measurements rather than from static call-site counts alone.

## Final verification

The final reviewed source passed all 683 libmylite Release tests, eight PHP
extension integration tests, the repository clang-format and clang-tidy gates,
and nine focused ASan/LeakSanitizer tests covering predicate plans,
transactions and concurrent access, statement caches, aggregates, scalar
subqueries, cursor teardown, and SQLite bootstrap. Unloaded benchmark smokes
retained the measured scaling and completed the concurrent scenario without
errors.
