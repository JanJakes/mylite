# Whole-Project Engineering Assessment, July 2026

## Executive verdict

MyLite has a strong compatibility-development foundation and an unusually broad
test and specification inventory for an early project. Its SQLite boundary is
disciplined, the SQLite patch stack is currently empty, persistent DDL generally
couples catalog and physical-schema changes transactionally, the public C ABI is
small and visibility-controlled, and recent profiling work materially improved
the measured WordPress path.

The project is not yet ready to be treated as a safe general-purpose MySQL
drop-in or as a release-quality embedded database. This review reproduced seven
stop-ship defects:

1. PHP parameter APIs can execute injected SQL when the session uses
   `NO_BACKSLASH_ESCAPES`.
2. an executable-comment query causes an AddressSanitizer-detected global
   buffer overflow;
3. closing a database with a live statement causes an AddressSanitizer-detected
   heap use-after-free;
4. mysqli autocommit reports success while leaving writes in autocommit mode;
5. failed first-open cleanup can unlink another opener's replacement database;
6. stale concurrent AUTO_INCREMENT planning can overwrite another writer's row
   through `ON DUPLICATE KEY UPDATE`;
7. an internal rollback failure can leave an earlier row from a failed
   statement visible while the handle continues in an undisclosed transaction.

The review also confirmed a file-format boundary defect: the 4096-byte shifted
SQLite payload maps a valid logical database page over SQLite's physical
pending-lock byte range. Its practical effect is platform and filesystem
dependent, but the address-space mismatch is deterministic and must be resolved
before large files are supported.

The repository's license is still `TBD`. Independently of technical quality,
that blocks a redistribution-ready release until the project and all shipped
artifacts have an explicit license and license inventory.

The immediate priority is therefore correctness and containment, not additional
compatibility breadth. After the stop-ship defects, the most important work is
to make transaction behavior truthful, harden file creation/recovery and
catalog validation, introduce a real binding API, and make sanitizers,
concurrency, crash recovery, and compatibility traceability release gates.

## Scope and method

This assessment covers commit
`7d81365844dd8ec9179e5bdd25455aeaf305de55` on `main`. It evaluates:

- architecture and module boundaries;
- SQL normalization, lexing, parsing, analysis, planning, and lowering;
- runtime correctness, diagnostics, result lifetimes, and MySQL semantics;
- `.mylite` storage, SQLite integration, concurrency, durability, and recovery;
- catalog and metadata behavior;
- the public C API and PHP integration packages;
- successful-query performance and pathological scaling;
- build structure, dependencies, artifact size, and packaging;
- tests, compatibility evidence, CI, and release qualification.

The review used two independent audit rounds. The first divided the codebase by
subsystem. The second challenged the highest-severity findings, searched for
counterexamples and existing mitigations, and checked whether severity was
supported by an executable reproduction or a source-level invariant. Local
verification then reproduced the public failures and measured current build
artifacts.

Findings use these evidence labels:

- **Reproduced:** observed on the audited commit with a focused executable or
  PHP probe.
- **Source-proven:** the relevant control flow or address mapping is
  deterministic in the audited source, but the final user-visible failure may
  depend on platform, workload, or injected faults.
- **Risk:** credible design or coverage concern that still needs a targeted
  reproducer or measurement before implementation is justified.

Severity describes release impact, not implementation difficulty:

- **P0:** stop-ship safety, security, storage, or API-truthfulness defect.
- **P1:** high-priority correctness or architecture work needed before a broad
  release claim.
- **P2:** important scalability, maintainability, packaging, and evidence work.
- **P3:** narrower optimization or cleanup that should follow measurement.

## Strengths to preserve

### Compatibility discipline

- The project states a precise MySQL target, currently MySQL 8.4.9, rather than
  claiming generic MySQL compatibility.
- Compatibility is designed through feature specifications and paired native
  and MySQL-runtime expectations. The 958 specs and 792 MySQL scripts are a
  substantial evidence base.
- Compatibility documentation is generally explicit about placeholders and
  embedded-design limitations instead of silently equating accepted syntax
  with full behavior.
- WordPress, Drupal, Laravel, Doctrine DBAL, and MediaWiki jobs exercise real
  integration surfaces in CI.

### SQLite integration and storage transactions

- SQLite is pinned and vendored with an explicit manifest. The current patch
  stack is empty, which keeps upstream provenance and update work clear.
- MyLite-specific SQL behavior is overwhelmingly outside the SQLite fork.
- Ordinary persistent DDL updates the MyLite catalog and physical SQLite schema
  inside one mutation transaction. Cross-handle cache refresh uses
  `PRAGMA data_version` plus the durable catalog generation.
- Read transactions establish a SQLite snapshot before synchronizing metadata,
  preserving a coherent catalog/data view.

### ABI and build hygiene

- The C API uses opaque handles and explicit status values.
- Exactly 52 intended `mylite_*` symbols are dynamically visible from the core
  PHP module; internal first-party symbols remain hidden.
- GCC, Clang, Apple Clang, and Windows Clang builds use strict warnings. The
  repository also has clang-format and broad clang-tidy gates.
- Runtime dependencies are lean and appropriate for an embedded library.

### Tests and recent performance work

- Every native C test source is registered in CMake, and test volume exceeds
  runtime source volume.
- Recent profiling removed important algorithmic and fixed-cost problems:
  linked AST indexing for large `IN` lists, exact-fit growth of descriptor-heavy
  plan arrays, duplicate catalog synchronization, repeated catalog descriptor
  loading, and repeated SQLite preparation on several paths.
- The controlled July WordPress comparison measured a 21.9% improvement for
  the six-query frontend fixture and 35.8% for the eleven-query medium fixture.
  Large `IN` and wide-projection scenarios improved by 34.7x and 10.3x.
- On the measured successful WordPress frontend path, no remaining static
  micro-optimization is more important than the correctness work in this
  assessment.

## P0 stop-ship findings

### 1. PHP parameter binding is SQL interpolation and is injectable

**Evidence:** Reproduced in all three PHP APIs.

The core PHP statement implementation replaces every `?` byte with a rendered
SQL literal and escapes quotes with a backslash
([`php_mylite.c`](../../packages/php-ext-mylite/src/php_mylite.c)). The mysqli
replacement stores only the source string at prepare time, performs the same
literal interpolation on every execution, and then executes the rebuilt SQL
([`mysqli_support.c`](../../packages/php-ext-mysqli-mylite/src/mysqli_support.c)).
PDO ultimately executes its emulated active query string while its quote path
uses the same backslash escaping
([`php_pdo_mylite.c`](../../packages/php-ext-pdo-mylite/src/php_pdo_mylite.c)).

With `SET SESSION sql_mode = 'NO_BACKSLASH_ESCAPES'`, a bound value containing a
quote followed by SQL closes the generated literal. A local probe bound
`missing' OR 1=1 -- ` to a one-row predicate; core MyLite, mysqli, and PDO each
returned both table rows.

The defect requires a string parameter, the unsafe SQL mode, and a statement
shape in which the remaining text forms valid SQL. Numeric, Boolean, and NULL
parameters are not rendered as quoted strings. This qualification narrows the
trigger, not the release impact: applications expect parameter binding to keep
data non-executable under every supported session mode.

This is both a security defect and an architectural failure. Session-sensitive
escaping cannot make textual substitution equivalent to binding. It also gives
incorrect prepare-time errors, marker handling, binary values, numeric types,
SQL-mode behavior, and performance.

**Required correction:**

1. Add typed parameter binding to the public `mylite_stmt` API. Bind values to
   lowered SQLite parameters or MyLite expression slots; do not reconstruct SQL.
2. Make PHP core, mysqli, and PDO use that API.
3. Parse and prepare at prepare time. Preserve the MySQL distinction between
   prepare errors and execute errors.
4. Cover positional markers inside literals, quoted identifiers, comments,
   executable comments, binary strings, embedded NULs, every SQL mode affecting
   quoting, repeated execution, schema invalidation, and all PHP type mappings.
5. Until native binding exists, reject prepared execution under unsafe modes or
   mark the PHP adapters experimental. Escaping changes are not an adequate
   final fix.

### 2. Executable-comment spans can read beyond the SQL buffer

**Evidence:** Reproduced under ASan.

Executing `SELECT /*!80000 1 */ + 2` produced a global-buffer-overflow in
`mylite_execution_copy_source_span_text()`, reached while constructing the
scalar projection column name. The nested executable-comment lexer reports
payload-relative token offsets, but the resulting AST span is later interpreted
against the original complete SQL buffer.

This is a memory-safety issue in a normal SQL input surface. The immediate
failure was an out-of-bounds read, but source-span corruption can affect
diagnostics, generated names, and any later consumer that trusts the span.

**Required correction:**

1. Give nested lexers an absolute base offset or rebase every emitted token and
   AST span before it leaves the nested parser context.
2. Validate every source span at construction and before copying: offset must be
   within input length and length must fit without overflow.
3. Add ASan/UBSan regressions for executable comments in scalar projections,
   aliases, nested comments, DDL, predicates, invalid input, and retry parses.
4. Fuzz the normalizer/lexer/parser pipeline with span validation enabled.

### 3. Database close does not own or invalidate live statements safely

**Evidence:** Reproduced under ASan.

A local C probe opened a database, prepared `SELECT 1`, closed the database, and
then finalized the statement. Finalization wrote connection diagnostics through
the freed `mylite_db`, producing a heap-use-after-free. The public header does
not document a close ordering contract, and even a documented caller contract
would not make an easily triggered C UAF an acceptable default.

**Required correction:** choose and enforce one explicit ownership model.

- Preferred: register live statements with the connection. `mylite_close()`
  either finalizes them deterministically or returns a busy/misuse error from a
  new fallible close API. Statement finalization unregisters itself.
- Alternative: statements hold a reference-counted connection core whose
  SQLite handle and diagnostics outlive the public database object.

All statement accessors, step, reset, and finalize operations need closed-state
tests. PHP object teardown must exercise both destruction orders.

### 4. The shifted payload overlaps SQLite's physical lock bytes

**Evidence:** Source-proven address mapping; platform effect requires dedicated
cross-platform testing.

MyLite shifts main-database reads, writes, truncates, and size controls by 4096
bytes in
[`mylite_offset_vfs.c`](../../packages/libmylite/src/storage/mylite_offset_vfs.c),
but delegates `xLock`, `xUnlock`, and `xCheckReservedLock` unchanged. SQLite
reserves physical bytes beginning at `0x40000000`; its pager skips the logical
page containing that same unshifted address.

Consequently:

```text
MyLite logical 0x3ffff000 + 0x1000 header = physical 0x40000000
```

The logical page MyLite writes at that address is not the page SQLite skips.
On POSIX advisory-lock implementations a write may appear to work, while on
mandatory-locking platforms such as Windows it can fail. Filesystems and VFSes
can also differ in how overlapping locks and writes behave. This makes the
current large-file boundary unsafe even if ordinary small databases pass.

**Required correction:**

1. Add an explicit SQLite extension point for the physical lock-byte base used
   by the wrapped main file, or redesign the file layout so logical and physical
   reserved pages align.
2. Until the format is corrected, enforce a logical maximum size below the
   first colliding page and return a deterministic MyLite diagnostic.
3. Test below/at/above the boundary on Windows and POSIX, with rollback journal
   and all supported page sizes.
4. Review sector size, device characteristics, size hints, and any future mmap
   or shared-memory methods under the same shifted-address model.

### 5. `mysqli_autocommit()` reports success without changing state

**Evidence:** Reproduced; the implementation explicitly discards the argument.

Both procedural and object methods return true without executing transaction
control. A local probe called `autocommit(false)`, inserted a row, called
rollback, and still observed the committed row. This silently violates the
transaction contract and can cause irreversible application writes.

**Required correction:** route both methods through the same core transaction
state machine as `SET autocommit`. Add tests for false/true transitions, pending
transactions, implicit commit, rollback, DDL, errors, close, and independent
handles. Audit other mysqli methods that return success while discarding their
arguments; unsupported operations should fail truthfully, not claim success.

### 6. Failed first-open cleanup can delete another database

**Evidence:** Reproduced with a deterministic POSIX identity-replacement probe.

The creation path creates and closes a file, later opens SQLite by pathname, and
on failure removes that pathname without proving it still names the inode this
opener created. A probe renamed the created inode, installed a replacement at
the original path, and entered failure cleanup. The replacement was deleted.

This can delete the winning database during concurrent first-open or pathname
replacement and can also produce split-brain handles. Windows sharing rules
change some rename/unlink cases, but do not make the validate/open identity gap
sound.

**Required correction:** create, validate, and open through one identity-bound
handle or an equivalent exclusive VFS operation. Cleanup may unlink only after
proving ownership of the same file identity. Add deterministic multi-process
open barriers plus rename, symlink, replacement, permission, and injected-open
failure tests on POSIX and Windows.

### 7. Concurrent AUTO_INCREMENT planning can overwrite a committed row

**Evidence:** Reproduced with a deterministic trace barrier.

AUTO_INCREMENT metadata and generated IDs are planned before `BEGIN IMMEDIATE`.
The verifier paused writer A after it planned `id=1`, allowed writer B to commit
`id=1`, and resumed A. A plain insert correctly failed as a duplicate, but
`ON DUPLICATE KEY UPDATE` succeeded and overwrote B's value. A stale generated
identity was treated as the user's duplicate target.

This is logical data corruption, not merely a difference from InnoDB lock-mode
details.

**Required correction:** obtain the serialized writer boundary before reading
or reserving the high-water mark, and keep reservation, row mutation, and
counter advancement in one defined transaction protocol. Qualify plain INSERT,
IGNORE, REPLACE, ODKU, multi-row, explicit values, rollback, savepoints, close,
and process death with deterministic two-handle schedules.

### 8. Failed internal rollback can leak statement changes

**Evidence:** Reproduced through SQLite authorizer fault injection.

Statement rollback discards the outcomes of `ROLLBACK TO`, `RELEASE`, and
`ROLLBACK`, then marks its transaction state inactive. With rollback denied
after row one of a failing multi-row insert, the first row remained visible,
SQLite remained outside autocommit, and the MyLite handle did not report that
its transaction state was uncertain.

**Required correction:** propagate both primary and cleanup outcomes. Preserve
the original failure, append rollback context, and poison the connection if
atomicity cannot be established. A poisoned handle must reject further SQL and
require close/reopen. Add VFS/authorizer fault points around write, sync,
truncate, savepoint rollback/release, full rollback, commit, and close.

### Non-technical release blocker: no project license

The README still states `License: TBD`. Before distributing source or binaries,
choose the project license, verify every bundled component and generated
artifact against it, and ship a license inventory/SBOM. CI green status cannot
substitute for permission to redistribute.

## P1 correctness and architecture findings

### SQL normalization duplicates parser responsibilities

Several pre-parser text rewrites implement SQL-sensitive behavior without a
shared lexer or session-aware token stream:

- A statement consisting only of an executable comment has its body extracted
  before parsing, but the version gate is discarded. The review reproduced
  `/*!99999 SET @future_gate = 7 */` executing and assigning 7 even though the
  configured MySQL gate is 8.4.9 and a future-version comment should be skipped.
- Bare `SET` value quoting scans for `=` bytes without skipping SQL strings and
  comments. The review reproduced
  `SET @x = 'default_storage_engine=InnoDB'` becoming invalid SQL.
- `sys.*` helper calls are renamed in normalized SQL. Without an explicit alias,
  `SELECT sys.format_bytes(1024)` exposed the internal generated column name
  `_mylite_sys_format_bytes(1024)`.
- Quote and backslash handling is not consistently parameterized by session SQL
  mode.

Move SQL-sensitive rewrites after lexing or represent them as AST/analyzer
transformations. One session-aware tokenizer should define strings, identifiers,
comments, markers, and executable-comment gates. Original source spans and
display names must remain separate from lowered internal names.

### The advertised analyzer boundary is not a stable intermediate layer

The README describes parse, analyze, plan/translate, and execute phases. In the
implementation, substantial semantic classification, name resolution, type
decisions, SQL construction, and special execution dispatch remain distributed
across AST helpers and a very large execution translation unit. This makes it
hard to state which invariants are guaranteed before lowering, reuse analyzed
plans, or test semantics independently of SQLite SQL generation.

MyLite already has a de facto analyzed representation: resolved predicate and
SELECT plans plus a large planned-scalar-expression family. Do not add a second
universal IR beside it. Promote those existing plan families into a stable,
typed boundary with explicit ownership:

- resolved catalog object IDs and immutable metadata references;
- typed expressions and coercions;
- parameter slots;
- collation and character-set decisions;
- warning/error sites with original source spans;
- transaction and statement side-effect declarations;
- a schema/session generation key for safe reuse.

Plans currently retain AST pointers in several families, and runtime code has
thousands of direct `mylite_sql_*` references. Migrate one statement family at
a time until its executor no longer needs the AST. This is the architectural
prerequisite for real prepared statements, better diagnostics, more reliable
lowering, and smaller execution modules without a high-risk semantic rewrite.

### `mylite_execution.c` is a mega translation unit

`mylite_execution.c` directly includes 283 `.inc` fragments. The directly
included source is approximately 261,000 lines, and its Release archive member
is about 3.84 MB. This arrangement gives private helpers cross-fragment reach
but weakens ownership boundaries, increases rebuild and static-analysis cost,
and allows session state and planner internals to spread without narrow APIs.

The split should follow semantic ownership, not arbitrary file length:

1. statement entry and statement context;
2. analyzer and analyzed IR;
3. SELECT/DML/DDL planners;
4. SQLite lowering and binder;
5. metadata providers;
6. execution completion and diagnostics.

Each module should expose a small internal header and compile independently.
Do this incrementally behind tests; a wholesale mechanical split would create
review risk without improving invariants.

### Session and statement completion state is too diffuse

The runtime contains more than 760 direct session-state accesses across 101
files. Materialized cursors may release their SQLite transaction and coexist
with later commands, but their later step/finalize completion can still update
connection-level `ROW_COUNT()`, `FOUND_ROWS()`, and diagnostics. This lets
completion order overwrite statement order.

Create a statement-owned completion record. Connection-visible state should be
published once, at the MySQL-defined command boundary, and stale cursors should
not republish it. Extract ownership and lifecycle for mutable collections such
as variables, prepared programs, transactions, and temporary catalog state.
Do not mechanically replace every embedded session-field access with an
accessor; the embedded, handle-local state model is sound.

### The public C error and lifetime contract is incomplete

`mylite_open()` returns only a status and no handle on failure, leaving nowhere
to retrieve the detailed diagnostic promised by the handle-owned error model.
`mylite_close()` is infallible even when SQLite close or transaction cleanup
fails. Returned text/byte pointers lack concise lifetime and nullability
documentation, and the API does not state a threading or reentrancy contract.

Evolve additively: preserve existing opaque handles and signatures, add
fallible/ex variants only where the old ABI cannot report a required outcome,
and document ownership for every returned handle and borrowed pointer. Avoid a
broad ABI rewrite or universal value type; statement parameters, result cells,
JSON values, and AST nodes have different ownership and semantic needs.

### File creation, interrupted initialization, and recovery are underspecified

Beyond the P0 pathname-deletion defect, validation and SQLite open are separate
operations. The verifier changed the preamble magic after validation and SQLite
still opened the payload. A valid 4096-byte preamble-only file also opened as a
new database and grew to 122,880 bytes. That makes interrupted creation or
truncation indistinguishable from intended initialization. Catalog
migration/state inspection also needs one writer-owned decision point.

Specify a file lifecycle state machine in the preamble: uninitialized,
initializing, committed format version, and recovery-required. Use exclusive
creation or an equivalent VFS primitive, never unlink a path based only on an
earlier ownership assumption, and make reopen either complete a proven-safe
initialization or reject deterministically.

### AUTO_INCREMENT close and crash durability remain incomplete

In addition to the concurrent stale-planning P0, clean close can roll back a
transaction and free the in-memory high-water state without reconciliation. A
probe reopened the file and reused `id=1`, contrary to the clean-close lifecycle
specification. Reuse after process death is also confirmed but is currently a
documented limitation rather than an undocumented defect.

After fixing writer serialization, define the durable high-water invariant for
commit, rollback, duplicate-key updates, explicit values, savepoints, clean
close, and process death. Reconcile clean close through a status-returning path;
then decide and document whether crash-time gap preservation is a format
guarantee or an explicit incompatibility.

### Single-file means clean state, not every instant

MyLite forces DELETE journaling, provides no shared-memory VFS methods, and
disables mmap. During a write, SQLite's rollback journal is required recovery
state outside the `.mylite` file. This is documented and is not itself a
corruption defect, but portability is only single-file after clean transaction
completion/close. State that boundary prominently and include hot-journal
recovery in crash tests. Any future WAL or mmap work must be designed with the
shifted VFS and single-file product contract rather than enabled as a tuning
flag.

### Catalog opening validates shape more than integrity

Open-time validation checks the presence of required catalog columns but does
not verify complete declared types, PK/UNIQUE/CHECK constraints, required
indexes, or relationships among schema/table/column/index/foreign-key rows.
Most logical relationships are not enforced by SQLite foreign keys.

The verifier dropped a catalog-described physical table directly and reopened
the file successfully; only the later public SELECT failed. Open validation
therefore accepts a confirmed catalog/physical-schema inconsistency.

Define a normalized catalog schema fingerprint from `table_xinfo`,
`index_list`, and `index_xinfo`, plus explicit row-invariant checks for object
references, unique names, and ordinal sequences. Corruption tests should remove
constraints and indexes while preserving column names and should insert orphan
rows. Opening must reject all such files before metadata is used.

The stored `minimum_reader_schema_version` contract also needs correction. A
newer schema is rejected before the minimum-reader value can permit an older
reader, so the current N-1 declaration does not provide N-1 compatibility.
Specify separate reader and writer rules and test actual N and N-1 binaries.

### Synthetic metadata has incorrect result descriptors

The review prepared an `INFORMATION_SCHEMA.TABLES` query through the public C
cursor API. Its `TABLE_NAME` result reported:

```text
type=-1 flags=0 charset=0 collation=0 display_length=0 nullable=1
```

That is name-only metadata, not MySQL-compatible column metadata. ORMs and PHP
drivers can inspect type, flags, charset, collation, length, precision, and
nullability even when row text is correct.

Metadata providers should use typed static descriptors or derive descriptors
from the provider schema. Add MySQL-paired tests for result metadata, not only
rows, across SHOW, INFORMATION_SCHEMA, Performance Schema, and sys queries.

### Metadata execution relies on brittle bridges and eager row sets

Some ORM-oriented INFORMATION_SCHEMA join paths are selected by raw SQL
substring patterns. Equivalent whitespace, comments, aliases, quoting, or
predicate order can miss the path, while matching text in a literal/comment can
select it accidentally. The second audit round reproduced a comment-only spoof
that changed the projection, result schema, and returned rows and bypassed
`LIMIT 1`. Dispatch must depend on analyzed query structure.

Generic metadata execution also tends to build complete, full-width rows before
predicate evaluation, projection, aggregation, ordering, or LIMIT. Each cell is
duplicated. Exact TABLES existence probes have a useful direct path, but broad
`COUNT(*)`, `LIMIT 1`, COLUMNS, and STATISTICS workloads can scale with all
catalog rows and full provider width.

Replace substring bridges with analyzed relational plans and move metadata
providers toward iterators with predicate/projection/LIMIT/count pushdown.
Measure 100, 1,000, and 10,000-table catalogs before choosing cache or arena
details.

### Collation behavior is incomplete and `GROUP_CONCAT(DISTINCT)` is wrong

The registered `utf8mb4_0900_ai_ci` compatibility comparator folds ASCII case
only. MySQL 8.4.9 considered both `A=a` and `é=e` equal under that collation;
MyLite handled the ASCII case but not the accent. This limitation is accurately
documented, but its impact reaches comparisons, grouping, ordering, unique
constraints, and indexes, so it remains a major compatibility boundary.

`GROUP_CONCAT(DISTINCT)` has an additional confirmed defect. It stores every
accepted value in a linked list and uses bytewise `memcmp()` against every prior
value. A differential probe produced `A|a|é|e` in MyLite where MySQL produced
`A|é`. The implementation is also quadratic in distinct candidate count and
allocates one node/value per accepted candidate.

Build one shared collation-key/comparison service, then use collation keys for
comparison, grouping, uniqueness, and aggregate DISTINCT. `GROUP_CONCAT` should
use a hash set or a sort/deduplicate strategy with bounded accounting. Test
case, accent, Unicode normalization, trailing spaces, binary collations,
coercibility, invalid encodings, and large groups.

### Concurrency visibility is not consistently synchronized

The PROCESSLIST registry protects membership and handle lifetime with a global
SQLite mutex, but snapshot collection reads mutable schema, autocommit, and
transaction fields while their normal writers do not take that mutex. This is a
C data race in a multithreaded host. Snapshot allocation also occurs while the
global registry lock is held, and insertion sorting is quadratic.

Publish an immutable per-session snapshot under synchronization or give each
session a narrow lock/sequence protocol. Copy references under the registry
lock, allocate and sort after releasing it, and use `qsort` or an already-ordered
identifier structure. Qualify the design under TSan with concurrent session
mutation, connection open/close, and PROCESSLIST queries.

## Semantics requiring focused qualification

The following are credible P1/P2 semantic gaps. They should be converted to
minimal MySQL-paired reproducers before broad refactoring:

- The streaming C value API uses a null pointer for NULL while also exposing
  zero-length byte values, making NULL versus empty BLOB/text easy for adapters
  to conflate unless every caller also uses metadata and size correctly.
- Cursor fallback treats a broad class of preparation failures as "unsupported"
  and retries materialized execution. The fallback boundary must preserve the
  original diagnostic and trigger only on a typed capability result.
- No generated-SQL/binder mismatch was reproduced. The builder and binder do,
  however, traverse plans independently without a final
  `sqlite3_bind_parameter_count()` invariant. Generate binding descriptors with
  placeholders and assert exact count/order on preparation and cache reuse.
- SQL `PREPARE` stores source and reparses later under current session state,
  rather than freezing the appropriate prepare-time semantics.
- Decimal parsing and formatting must be locale-independent and reject partial
  conversions consistently.

## Performance assessment

### Current successful WordPress path

The July 2026 performance review is still the right conclusion for the measured
frontend workload: the chapter on successful WordPress CPU hot paths can close.
Parser/lexer cost is small, SQLite prepared programs are reused, source metadata
is generation-pinned, wide projections grow geometrically, and catalog
synchronization is no longer duplicated.

The defects in this assessment should not be recast as speculative performance
projects. Native binding, for example, is required first for security and API
semantics; avoiding repeated parse/plan work is a secondary benefit.

### Remaining measurable performance work

1. **Metadata scale:** iterator/pushdown work for INFORMATION_SCHEMA and SHOW.
   Measure allocation count, peak RSS, catalog rows stepped, and latency by
   table/column/index cardinality.
2. **Invalid SQL and parser recovery:** retry callbacks can repeatedly tokenize
   a statement, and nested-parenthesis probes can become superlinear. Measure
   successful, retry-success, and rejected input separately from 64 to 65,536
   tokens. Put hard depth/work limits on untrusted SQL.
3. **Descriptor footprint:** a catalog column descriptor is 15,624 bytes on the
   audited 64-bit build, mostly fixed inline string capacity. Split hot compact
   identity/type data from cold variable-length comments, defaults, and
   generated expressions. Budget caches by bytes, not table count.
4. **Prepared execution:** once native binding exists, cache analyzed plans by
   schema generation and relevant session state. Compare repeated mysqli/PDO
   execution against literal queries and direct SQLite binding.
5. **Administrative concurrency:** measure PROCESSLIST snapshot lock hold time
   and catalog-cache churn at 1, 16, 64, and 256 handles.

Do not optimize the normalizer scan, small string-builder calls, or fixed helper
lookups without profile evidence. They are not credible current bottlenecks.

## Build, size, and packaging assessment

### What is good

- The dependency set is lean.
- Hidden visibility works.
- SQLite is pinned and patch accounting is explicit.
- Generated Lemon output stays in the build tree.
- The PHP adapters outside the core module are small.

### Main size drivers

The largest core archive members are the execution mega-unit, generated Lemon
parser, static sys/Performance Schema metadata, spatial support, and parser
retry implementation. Generated parser action/lookahead tables alone account
for a large fixed data contribution. Static metadata definitions also encode a
broad MySQL catalog surface directly in the binary.

A clean serial Release build measured 386 seconds on the audit host. The
execution mega-unit took 115 seconds, parser generation 89 seconds, and SQLite
compilation 84 seconds, together accounting for about three quarters of the
build. The generated parser is approximately 94,000 lines/6.9 MB, and its
compressed action/lookahead tables contribute about 1.21 MB. Lemon table
compression is already enabled, so parser size needs grammar/state analysis,
not a missing compression flag.

Recommended size work, in order:

1. Establish reproducible size reports per object and ELF section in CI.
2. Add a controlled production profile using LTO, function/data sections, and
   linker garbage collection on every supported toolchain.
3. Split the execution translation unit so dead subsystems can be eliminated
   when optional features are disabled.
4. Generate compact metadata tables from typed source data and share repeated
   strings. Validate the generator output under sanitizers.
5. Evaluate compile-time feature groups only where an embedding user can accept
   a reduced compatibility surface. The default build must remain coherent.
6. Remove upstream SQLite test/fuzz artifacts from distribution archives even
   if the development repository continues to vendor the complete tree.

The parser grammar should not be weakened merely to shrink tables. First
measure state/rule contributors and determine whether duplicate fallback syntax
or generated representation can be reduced without compatibility loss.

### Packaging gaps

The core CMake target is static-only. There is no install/export package,
pkg-config or CMake package configuration, shared-library ABI target,
`SOVERSION`, or public ownership/threading documentation. PHP builds are
developer/CI modules rather than a versioned distribution flow.

Add installable headers and `MyLite::mylite` package exports, choose and document
static/shared policy, add ABI checking for any shared library, and test
installation from a clean consumer project. PHP packaging should discover the
installed core and PHP ABI rather than rely on checkout build paths.

### Generated-code and tooling gaps

- The parser custom command depends on the grammar and Lemon target, but not
  directly on the copied `lempar.c` template. A template-only change can leave
  stale output. Add the template as an explicit dependency.
- `MYLITE_BUILD_TOOLS=OFF` does not avoid Lemon because parser generation
  unconditionally needs it. Treat Lemon as a host build tool and cache generated
  output by grammar, Lemon source/template, compiler, and flags.
- The format glob includes `.c` and `.h` but omits the large first-party `.inc`
  surface. Include `.inc` files or replace them during modularization.
- Production presets do not enable LTO, garbage collection, or an explicit
  strip/package step.

## Test, CI, and release assessment

### Strong inventory, incomplete release evidence

The breadth of example-based tests is a major asset, but count is not the same
as an enforceable release claim. Regular CI runs only 15 of 792 real-MySQL
expectation scripts. There is no machine-readable mapping from each green
compatibility row to its spec, native test, MySQL fixture, and CI tier.

Current native CI tests Release builds. There is no repository sanitizer
preset/job despite the engineering standard requiring ASan/UBSan modes, no
coverage gate, no first-party fuzz/property harness, no crash/power-failure
harness, and very little deterministic threaded testing. Benchmarks are
developer tools with no automated regression comparison.

CI also produces no installable artifacts, hashes, provenance, SBOM, or clean
consumer test. Several Actions, runner images, package-manager inputs, Composer
images, and containers are selected by mutable major/latest tags. A release
workflow should pin toolchains and containers, build twice from clean trees,
compare reproducibility evidence, and upload signed or checksummed artifacts.

### Required quality tiers

1. **Every PR:** strict Debug and representative Release tests on Linux;
   existing compiler/OS matrix; format/tidy; changed-surface MySQL fixtures;
   a bounded ASan+UBSan suite; PHP/integration jobs; timeouts and failure
   artifacts.
2. **Nightly:** sharded full 792-script MySQL run; full ASan+UBSan; focused TSan;
   parser/runtime fuzz smoke; deterministic multi-handle stress; performance
   history on a stable runner.
3. **Release:** all nightly tiers plus crash/fault injection, file reopen and
   integrity verification, actual N/N-1 format binaries, installation/ABI
   tests, coverage report, size report, and a durable evidence manifest tied to
   the commit.

### Compatibility claim manifest

Assign stable identifiers to compatibility rows and store a checked manifest:

```text
claim -> specification -> MySQL 8.4.9 fixture -> MyLite test -> CI tier
```

Lint green claims for complete links and completed implementation/test/doc
tasks. Drive identical normalized fixtures against MySQL and MyLite where
possible rather than manually duplicating expected values in shell and C.

### Test architecture improvements

- Add CTest labels (`unit`, `runtime`, `mysql-paired`, `concurrency`, `slow`,
  `integration`) and per-test timeouts.
- Consolidate repeated path, cleanup, result, diagnostic, and assertion helpers.
- Generate repetitive CMake registration from a checked test manifest.
- Replace timing sleeps in concurrency tests with barriers and deterministic
  state transitions.
- Add allocator/VFS failpoints and model-based DDL/DML sequences.
- Begin fuzzing with the lexer/parser, normalizer, JSON/geometry decoders, and
  `.mylite` preamble/catalog inputs. Add metamorphic rollback/reopen and
  equivalent-expression checks.

## Recommended target architecture

The following evolution supports correctness, performance, and size together:

```text
SQL bytes + session lexical mode
    -> one tokenizer with absolute source spans
    -> parser AST
    -> promoted typed plan families
         resolved object IDs
         typed expressions/collations
         parameter slots
         side effects and diagnostics
    -> execution plan
         SQLite program + typed bindings
         MyLite operators/providers
         statement completion record
    -> result/cursor with explicit connection ownership
```

Supporting services should be explicit:

- immutable generation-pinned catalog snapshots;
- compact hot descriptors plus separately owned cold strings;
- a transaction coordinator responsible for begin/commit/rollback outcomes;
- a storage lifecycle component responsible for preamble state, VFS address
  mapping, recovery, and format compatibility;
- synchronized session publication for PROCESSLIST and monitoring;
- scoped allocation and VFS fault-injection hooks used by tests.

This architecture does not require replacing SQLite or rewriting the parser.
It removes semantic ambiguity between current stages and makes existing
compatibility code easier to validate.

## Prioritized roadmap

### P0: containment and safety

1. Disable unsafe PHP interpolation modes immediately, then implement native
   typed binding across C, core PHP, mysqli, and PDO.
2. Fix executable-comment span rebasing and add sanitizer regressions.
3. Make close/live-statement ownership safe.
4. Implement truthful mysqli autocommit behavior and audit success-returning
   placeholders.
5. Bind first-open and failure cleanup to one proven file identity.
6. Serialize AUTO_INCREMENT planning/reservation before any generated identity
   can collide with a concurrent writer.
7. Propagate rollback failures and poison transactionally uncertain handles.
8. Prevent files from reaching the shifted lock-byte collision; design the
   format/VFS correction and cross-platform boundary tests.
9. Choose the project license and verify the distribution license inventory.

### P1: transactional and semantic integrity

1. Replace SQL-sensitive text normalization with token/AST transformations,
   including executable-comment version gates and stable display names.
2. Centralize statement completion and prevent stale cursors from overwriting
   later connection state.
3. Define clean-close and crash-durable AUTO_INCREMENT high-water behavior.
4. Specify and harden interrupted initialization, preamble validation, hot
   journal recovery, and catalog migration recovery.
5. Add complete catalog schema/relationship validation and real N/N-1 tests.
6. Correct synthetic metadata descriptors and eliminate raw-SQL dispatch
   bridges.
7. Implement the shared collation service and correct aggregate DISTINCT.
8. Remove PROCESSLIST data races and qualify the supported threading model.

### P2: architecture and release qualification

1. Promote the existing plan families into a typed analyzer/plan/binding
   boundary and remove their AST dependencies incrementally.
2. Split the execution mega-unit incrementally.
3. Add sanitizer, fuzz, concurrency, crash, coverage, and full-MySQL CI tiers.
4. Make compatibility claims mechanically traceable.
5. Add install/export/ABI packaging and public ownership/threading docs.
6. Add reproducible object/section size reporting and a controlled production
   LTO/dead-code-elimination profile.

### P3: measured scalability and maintenance

1. Stream and push down metadata queries.
2. Compact catalog descriptors and static metadata.
3. Bound and optimize parser recovery after adversarial measurements.
4. Add generation-safe reusable analyzed plans.
5. Consolidate test helpers and generated registration.

## Verification record and limits

The final audit checkout passed:

- all 683 core CTests in the existing GCC Release build in 162.56 seconds;
- all 8 PHP extension integration CTests;
- `git diff --check` for the assessment change.

Focused disposable probes reproduced:

- SQL injection through core PHP, mysqli, and PDO string parameters under
  `NO_BACKSLASH_ESCAPES`;
- the executable-comment source-span overflow under ASan;
- the close/live-statement use-after-free under ASan;
- mysqli's false autocommit success and ineffective rollback;
- future-gated standalone executable-comment execution;
- allowlist-triggered SET string corruption;
- internal sys helper names leaking into result labels;
- name-only synthetic metadata descriptors;
- path-replacement deletion during failed first-open cleanup;
- stale concurrent AUTO_INCREMENT ODKU overwrite;
- row visibility and unknown transaction state after injected rollback failure;
- preamble validation/open replacement and preamble-only reinitialization;
- clean-close AUTO_INCREMENT reuse;
- reopening a catalog whose described physical table was missing;
- raw-comment spoofing of INFORMATION_SCHEMA bridge dispatch;
- collation and `GROUP_CONCAT(DISTINCT)` divergence from MySQL 8.4.9.

This audit did not claim a native Windows reproduction of the lock-byte failure,
run the entire 792-script MySQL corpus, execute a full sanitizer suite, or run
power-loss testing; those capabilities do not currently exist as repository
gates. Metadata scaling and prospective LTO/GC/MinSizeRel savings remain
measurement tasks, not established regressions or promised savings. The lock
mapping, missing gates, packaging surface, and other source-proven statements do
not depend on those unperformed experiments.

## Closure criteria

The project can move from "early compatibility development" toward a release
candidate only when all of the following are true:

- no known P0 memory-safety, injection, transaction-truthfulness, or storage
  address defects remain;
- the source and distributed artifacts have an explicit verified license;
- the full core and PHP suites pass under ASan+UBSan, with a focused TSan suite;
- live-handle destruction order is defined and tested for every public handle;
- native typed binding is used by all prepared-statement APIs;
- large files pass lock-boundary tests on Windows and POSIX;
- crash/fault tests prove catalog/physical-schema atomicity and deterministic
  reopen behavior;
- metadata rows and result descriptors are MySQL-paired;
- every green compatibility claim has an enforceable evidence chain;
- Debug, Release, installation, ABI, full-MySQL, and application tiers are
  represented in a release workflow;
- performance and size baselines are reproducible, and no regression is hidden
  by correctness shortcuts.

## Overall assessment

MyLite's direction is technically credible. The project has already shown that
it can convert profiling evidence into large end-to-end improvements while
keeping SQLite changes disciplined. Its specifications, native tests, MySQL
expectations, and application fixtures are a stronger base than most projects
at this stage.

The main risk is that breadth has advanced faster than lifecycle, security, and
release qualification. The reproduced PHP injection, two ASan failures, false
autocommit success, pathname deletion, concurrent generated-key overwrite,
rollback state leak, and shifted lock-byte mismatch are not edge polish. They
define the next engineering chapter. Addressing them through native binding,
explicit ownership, promotion of the existing plan boundary, and
storage/recovery qualification will also simplify performance work and make the
large compatibility surface more trustworthy.
