# Statement Diagnostics and Warning Snapshots

## Status

This feature specifies statement-owned error diagnostics and iterable warning
snapshots across the native MyLite API, PDO MyLite, and the mysqli replacement.
It closes review findings API-02 and API-05 without changing SQL syntax or
expanding the set of warnings MyLite produces.

## MySQL 8.4.9 Observations

The expectation script
`packages/libmylite/tests/mysql_statement_diagnostics_warning_snapshots_expectations.sh`
records the runtime probes for this feature.

PDO observations with native prepares and silent error mode:

- `PDOStatement::errorInfo()` reports the SQLSTATE, native code, and message
  for the last operation on that statement.
- A statement error does not change `PDO::errorInfo()`.
- Two live statements retain different errors. An operation on one does not
  replace the other statement's error.
- A successful execution clears only the executing statement's error. Errors
  on other live statements remain available.
- Re-executing a failed statement successfully replaces its error with
  `['00000', null, null]`.

mysqli observations:

- Direct `SELECT 1/0, CAST('NULL' AS UNSIGNED)` produces two warning records in
  evaluation order: `1365 / HY000 / Division by 0`, followed by
  `1292 / HY000 / Truncated incorrect INTEGER value: 'NULL'`.
- `mysqli::$warning_count` reports the total generated by the most recently
  executed operation. A later warning-free command changes it to zero.
- `mysqli::get_warnings()` returns the first real record. Repeated
  `mysqli_warning::next()` calls mutate the same object's public `errno`,
  `sqlstate`, and `message` properties in FIFO order, then return `false`.
- A non-strict prepared multirow insert can produce several ordered warning
  records. `mysqli_stmt::get_warnings()` exposes the statement's records while
  the connection warning count reports the total from execution.
- A later connection command does not alter a warning object already returned
  to the caller. That object also remains iterable after statement and
  connection close.
- Statement reset clears that statement's prior warning snapshot. Re-execution
  publishes a fresh snapshot.

## Scope

The implementation must:

- expose additive native statement accessors for error code, SQLSTATE, error
  message, total warning count, retained warning-record count, and an indexed
  warning-record copy;
- expose additive result accessors for retained warning-record count and an
  indexed warning-record copy so direct execution warnings remain available
  after the connection performs later work or closes;
- preserve the existing total warning count independently from retained-record
  capping by `max_error_count`;
- keep each prepared statement's completed diagnostic area independent from
  later work on the same connection or on another statement;
- clear a statement diagnostic snapshot on reset and replace it on
  re-execution;
- store PDO driver code and message on the handle whose operation failed,
  selecting statement storage for `PDOStatement::errorInfo()` and connection
  storage for `PDO::errorInfo()`;
- copy native warning records into mysqli connection and statement adapter
  state before native results or statements can be reset or finalized;
- make direct, object-oriented, prepared, and procedural mysqli warning APIs
  return real ordered warning records;
- make each returned `mysqli_warning` object own its warning chain so later
  adapter or native activity cannot invalidate it;
- cover independent live-statement failures, intervening success, direct and
  prepared multi-warning chains, reset, re-execution, statement close,
  connection close, total-versus-retained counts, and invalid indexed access.

## Non-Goals

This feature does not add:

- new SQL warning producers, a complete MySQL error catalog, or new SQL modes;
- `GET DIAGNOSTICS`, stored-program condition handlers, or stacked diagnostic
  areas;
- wire-protocol packets, mysqlnd internals, or a libmysqlclient-compatible ABI;
- an uncapped warning-record store when `max_error_count` limits retained
  diagnostics;
- thread safety or reentrancy for a single native database handle;
- changes to result, statement, or database ownership after close beyond the
  existing public contract.

## Public Native ABI

The installed header adds a caller-owned diagnostic value:

```c
enum {
    MYLITE_DIAGNOSTIC_SQLSTATE_CAPACITY = 6,
    MYLITE_DIAGNOSTIC_MESSAGE_CAPACITY = 256,
};

struct mylite_diagnostic {
    int error_code;
    char sqlstate[MYLITE_DIAGNOSTIC_SQLSTATE_CAPACITY];
    char message[MYLITE_DIAGNOSTIC_MESSAGE_CAPACITY];
};
```

Prepared statement accessors:

```c
int mylite_stmt_errcode(const mylite_stmt *stmt);
const char *mylite_stmt_sqlstate(const mylite_stmt *stmt);
const char *mylite_stmt_errmsg(const mylite_stmt *stmt);
size_t mylite_stmt_warning_count(const mylite_stmt *stmt);
size_t mylite_stmt_warning_record_count(const mylite_stmt *stmt);
int mylite_stmt_warning_at(
    const mylite_stmt *stmt,
    size_t index,
    struct mylite_diagnostic *out_diagnostic
);
```

Direct result accessors:

```c
size_t mylite_result_warning_record_count(const mylite_result *result);
int mylite_result_warning_at(
    const mylite_result *result,
    size_t index,
    struct mylite_diagnostic *out_diagnostic
);
```

All additions are exported at the existing ABI generation. Existing
structures, function signatures, status codes, and symbols are unchanged.

## Native Ownership and Lifetime

`mylite_stmt_errcode()`, `mylite_stmt_sqlstate()`, and
`mylite_stmt_errmsg()` read the statement's last completed diagnostic
snapshot. A newly prepared or successfully reset statement reports code zero,
SQLSTATE `00000`, an empty message, and zero warnings.

The returned statement SQLSTATE and message pointers are borrowed. They remain
valid until the next reset, step, or finalize on that statement, or database
close. Calls on the connection or another live statement do not invalidate or
change them.

`mylite_stmt_warning_count()` and `mylite_result_warning_count()` report the
total warning count, including warnings not retained because of
`max_error_count`. The corresponding `warning_record_count()` reports the
number of retained records that can be indexed.

`warning_at()` copies one retained record into caller-owned storage. It returns
`MYLITE_OK` on success and `MYLITE_MISUSE` for a null handle, null output
pointer, or out-of-range index. On misuse it zeroes a non-null output record.
The copied value is independent from later result, statement, or connection
activity, including reset, finalize, result free, and database close.

Successful direct result handles own a deep copy of their statement warning
area until `mylite_result_free()`. No result handle is returned for a failed
direct execution, so direct failures continue to use connection diagnostics.

## PDO Semantics

The PDO database driver state owns only database-handle diagnostics. Each
`pdo_mylite_stmt` owns its native code and copied message; PDO core continues
to own the five-character SQLSTATE field on the corresponding handle.

When a statement operation fails, the adapter copies the native statement
snapshot when available and otherwise copies the current connection diagnostic
or adapter fallback. A later connection operation or operation on another
statement cannot change that stored record.

Successful statement execution clears only that statement's PDO record.
Successful direct database operations clear only the database record.
`pdo_mylite_fetch_error()` selects storage from its `stmt` argument. A
successful handle returns SQLSTATE `00000` with null driver code and message.

## mysqli Semantics

The link owns the latest direct or prepared operation's total warning count and
a copied retained warning list. A prepared statement also owns a copy of its
latest completed warning list so it remains independently queryable.

Every command that publishes a new result clears the prior link warning list
before installing the new list. Statement reset clears the statement list.
Re-execution replaces it. Adapter allocation failure reports the existing
client out-of-memory diagnostic and does not expose a partial list.

`mysqli::get_warnings()` and `mysqli_get_warnings()` return `false` when the
link has no retained records. `mysqli_stmt::get_warnings()` and
`mysqli_stmt_get_warnings()` do the same for the statement. Otherwise each
creates an independent `mysqli_warning` object with a copied ordered chain.

The warning object's initial properties describe record zero. `next()` moves
to the next record and refreshes all three public properties. At the end it
returns `false` without changing the last record. Its owned chain is released
only when the warning object is destroyed.

## Error and Allocation Semantics

- Native indexed-access misuse is deterministic and does not replace
  connection or statement SQL diagnostics.
- Deep-copy failure while attaching diagnostics to a result or completion
  reports `MYLITE_NOMEM`, frees any incomplete public result, and preserves
  ordinary result ownership rules.
- PHP warning-chain allocation is all-or-nothing. Partial copies are released.
- Finalize, reset, result free, PHP statement destruction, link destruction,
  and warning-object destruction release each owned diagnostic allocation
  exactly once.
